# AiVisibility
(Даний проєкт був створений з навчальною ціллю, тому контрібутором є також Claude)

Рушій вимірювання того, як AI-асистенти згадують бренди, **з довірчими
інтервалами**. Пілот — fintech (платіжні провайдери: Stripe, Paddle).

Ідея: частота згадки бренду в відповідях AI — це статистична оцінка, а не
фіксоване число. Одна й та сама модель на те саме питання відповідає по-різному,
тому «Stripe згадано у 42% відповідей» без інтервалу нічого не означає. Проєкт
рахує такі оцінки разом із bootstrap-CI, каже, чи різниця між двома періодами —
зміна чи шум, і оцінює, скільки запитів потрібно для потрібної точності.

Методологічна основа — Sielinski, *Quantifying Uncertainty in AI Visibility*
([arXiv:2603.08924](https://arxiv.org/abs/2603.08924)). Звідти ідея (bootstrap-CI
і криві збіжності для метрик AI-видимості); тут вона перенесена на іншу задачу
(згадки брендів, а не цитування доменів), на движки Claude та OpenAI і на нішу
B2B fintech. Окремо додано адаптивний семплінг, перевірку репрезентативності
запитів і карту сприйняття брендів.

## Швидкий старт

```
uv sync                      # залежності (Python >= 3.12)
cp .env.example .env         # додати OPENAI_API_KEY (і ANTHROPIC_API_KEY за потреби)
uv run pytest                # тести (офлайн, без ключів)
uv run ruff check .          # лінтер
```

Порядок скриптів: `discover_brands` → `generate_queries` →
`run_prober --dry-run` (потім реальний запуск з `--max-budget-usd`) →
`detect_mentions` → `analyze_mentions` → `build_convergence_curves` /
`estimate_sample_size` → `adaptive_sampling_report` →
`collect_real_queries` → `representativeness_report` →
`run_pairwise --dry-run` (потім реальний запуск) → `perception_report` →
`export_dashboard_data`. Скрипти, що викликають Claude/OpenAI, коштують
грошей: завжди спершу `--dry-run`. Процес розробки — `docs/sdlc.md`,
специфікації розділів — `docs/sections/`.

Дані для дашборду: `uv run python scripts/export_dashboard_data.py` кладе
`data/reports/dashboard.json` (без викликів API, ≈3 хв). Експортовані секції:
видимість брендів, криві збіжності, карта сприйняття, репрезентативність,
адаптивний семплінг (симуляція) і тональність (мітки Claude, частки з CI).
Сторінок для двох останніх секцій у дашборді ще немає.

Дашборд (Laravel, лише показує цей JSON): `docker compose up -d --build dashboard`,
далі <http://localhost:8080>. Файл читається при кожному запиті, тож після нового
експорту достатньо оновити сторінку.

## Що вже є на ринку і чим це відрізняється

Комерційні трекери AI-видимості (Otterly.AI, Profound, Evertune, Semrush One та
інші) і open-source проєкти (limelitgeo/open, llm-brand-tracker та ін.), які
ми переглянули, за їхніми публічними описами показують mention rate або
citation share як точкову оцінку, без довірчих інтервалів. Ми не стверджуємо,
що вони гірші: у них кращий інтерфейс, більше движків і постійний моніторинг,
чого цей проєкт не має. Різниця лише в тому, що саме ми вимірюємо:

| | Типовий трекер | Цей проєкт |
|---|---|---|
| Оцінка видимості | точкова | з bootstrap-CI |
| «Видимість змінилась» | різниця двох чисел | інтервали перетинаються → шум |
| Скільки запитів досить | не обговорюється | емпіричні криві збіжності по движку |
| Вартість вимірювання | фіксована | адаптивний семплінг (у симуляції дешевше) |
| Чи схожі запити на реальні | не перевіряється | two-sample test на реальних питаннях |

Це перші, наскільки нам відомо, емпіричні орієнтири розміру вибірки саме для
Claude й OpenAI на задачі згадок брендів у fintech, але **не** строге
параметричне правило мінімального n: його автор статті сам залишив майбутній
роботі, і ми його не виводимо.

## Методологія

### Скільки запитів потрібно на движок (Розділ 4)

Довірчий інтервал mention rate конкурента звужується зі зростанням n
приблизно за формою `1/sqrt(n)`. На наявних даних пілоту (Stripe/Paddle,
2 бренди) ціль ±5 в.п. ще не досягається: на n=36 (Claude) ширина CI ≈9.7
в.п., на n=24 (OpenAI) — ≈9.2 в.п. Екстраполяція форми кривої дає
орієнтир ≈126 запитів на движок для Claude і ≈71 для OpenAI. Це **емпіричний
орієнтир для нашого сетапу** (ці два бренди, fintech-ніша, ці движки), а
не універсальна формула. Біноміальна оцінка на спостережених частотах дає
приблизно вдвічі більше (≈270 і ≈128), тому для планування розумно брати
вище значення. Деталі — `docs/sections/section4.md`.

### Адаптивний семплінг (Розділ 5)

Замість рівномірного round-robin по (бренд, движок)-парах, адаптивна
стратегія на кожному кроці йде туди, де зараз найширший bootstrap CI серед
ще не стабілізованих конкурентів ("expected variance reduction"). За
однаковий фіксований бюджет викликів це дає суттєво точніший результат:
для середньої ширини CI по всіх 20 відстежуваних сутностях ціль ±5 в.п.
досягається на **68% менше викликів** (143 проти 451); для найгіршого
(max) відстежуваного конкурента — на **42% менше** (~891 проти ~1542, обидва числа — екстраполяція,
не пряме спостереження). Цікавий побічний, чесно задокументований
результат: якщо метою є "щоб КОЖЕН конкурент незалежно досяг цілі"
(а не фіксований спільний бюджет), переставляння порядку викликів
різниці не дає — арми статистично незалежні, тож сумарна кількість
викликів адитивна й не залежить від порядку. Це **симуляція на вже зібраних
даних**, а не живий A/B-тест на API. Деталі — `docs/sections/section5.md`.

### Репрезентативність запитів (Розділ 6)

Чи схожі наші 106 синтетичних запитів на реальні питання людей? Збираємо 474
питання з Hacker News і Stack Overflow, навчаємо класифікатор відрізняти їх від
синтетичних на embeddings (classifier two-sample test): AUC **0.99**, p<0.01 —
набір легко відрізнити, і це не пояснюється лише довжиною чи типом питань.
Перезважування mention rate за кластерами реальних тем піднімає оцінки
конкурентів Stripe, але величина залежить від кластеризації (звіт містить
таблицю чутливості), тому ми не подаємо єдине «виправлене» число. Обмеження:
форумні питання ≠ промпти до асистента, Reddit не включено. Деталі —
`docs/sections/section6.md`.

### Карта сприйняття брендів (Розділ 7)

Як AI-асистент порівнює Stripe, Paddle, Adyen і PayPal за 7 атрибутами
(ціна, виплати, надійність, інтеграція, підтримка, регуляторна довіра,
стартап vs enterprise)? 840 попарних запитів «A чи B?» на движок, кожна комірка
в обох порядках, агрегація Bradley-Terry з bootstrap-CI по комірках. Головне:
рейтинги Claude й OpenAI здебільшого збігаються (Spearman 0.8-1.0, окрім
`good_support`), циклів у перевагах немає, а **чітко розділені лише 25 з 84
пар брендів** (CI не перекриваються) — решту ранжувати не можна. Позиційне
упередження невелике, але ненульове (Claude 0.44, OpenAI 0.54 частки «A»).
Claude відповідає майже детерміновано, тому у 5 із 7 атрибутів величина `θ`
задана регуляризацією, і карта показує там лише порядок. Це що модель
*каже*, а не факт. Прогін коштував ≈ $6.7 (Claude) і <$0.01 (OpenAI). Деталі —
`docs/sections/section7.md`.

### Класифікатор тональності

Модель визначає, як ШІ подає бренд (`recommended` / `neutral` / `negative`):
розмітка через Claude, навчання, оцінка на ручному gold-наборі. Чесне число —
gold macro-F1 ≈0.58 для fine-tuned моделі (розкид за seed ≈9 пунктів), а не
0.80-0.86 крос-валідації, яку роздувають синтетичні рядки. Команди, результати
й відкриті питання — `docs/stance_classifier.md`.

## Висновки

Зроблено: від підбору брендів і генерації запитів до пробера (Claude, OpenAI),
bootstrap-CI, кривих збіжності, адаптивного семплінгу, перевірки
репрезентативності, карти сприйняття, класифікатора тональності та
Laravel-дашборду. Що показав пілот (Stripe, Paddle):

- **Згадки залежать від движка:** у запитах про Paddle Claude згадує Stripe у
  81% відповідей, OpenAI — у 26%; інтервали не перетинаються, тож це не шум.
  Видимість треба міряти окремо для кожного движка.
- **AI бачить Stripe сильнішим за Paddle** за надійністю, підтримкою й
  регуляторною довірою; за ціною та інтеграцією різниці немає.
- **Тональність переважно нейтральна**; збіг міток Claude з людиною
  κ = 0.74.
- **Для точності ±5 в.п.** потрібно ≈120-155 відповідей на движок;
  адаптивний семплінг економить ≈40-75% запитів лише за фіксованого бюджету.
- **Синтетичні запити легко відрізнити від реальних** (AUC 0.93-0.99), тому
  результати треба перевіряти на реальніших запитах.

Загальний висновок: без довірчих інтервалів числа видимості в AI — шум.

## Обмеження

- **Це що модель каже, а не що правда.** Відповіді відбивають навчальні дані,
  а не поточний стан продуктів; фактичну точність (комісії, країни) ми не
  перевіряли.
- **Малий пілот:** 2 бренди для mention rate, 4 бренди в карті сприйняття,
  n=24-36 відповідей на групу. Орієнтири n — екстраполяція, не спостереження.
- **Лише чисті chatbot-відповіді** (без retrieval і web search): це не те саме,
  що Google AI Overview чи Perplexity.
- **Немає довгих часових рядів.** Порівняння «двох періодів» у Розділі 3 — це
  два прогони одного дня; демонстрація методу, не доказ зміни видимості.
- **Детекція згадок — пошук підрядка**, без NER; пропустить непрямі згадки.
- **Не контролюємо температуру й seed API**, тому повторний прогін дасть трохи
  інші числа.
- **Репрезентативність:** синтетичні запити легко відрізнити від реальних
  (AUC 0.99); перезважування залежить від кластеризації, тож «виправленого»
  числа ми не даємо.
- **Симуляція адаптивного семплінгу** проведена на вже зібраних даних.

## Future Work

1. **Географія / мова запиту.** Видимість платіжного провайдера залежить від
   країни (США vs ЄС vs Україна); розширити Prober на мультимовні й
   геолокалізовані запити та порівняти довірчі інтервали між регіонами.
2. Zero-inflated моделювання рідко цитованих доменів.
3. Довгострокові часові ряди (сезонність, ефекти оновлень моделей).
4. Інші fintech-підніші (перекази, необанки) для перевірки узагальнюваності.
5. Строге параметричне правило мінімального n як функція параметрів
   розподілу згадок.
6. Окремий «AI-пошук» пробер із retrieval / web search.
7. Fact-check комісій і країн проти офіційних pricing-сторінок.
8. Gemini як третій движок.
