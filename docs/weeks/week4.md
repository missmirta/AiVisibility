## Мета тижня

Побудувати для кожного движку (Claude, OpenAI) окрему криву "ширина
bootstrap CI → розмір вибірки n" і на її основі дати перший емпіричний
орієнтир "скільки запитів потрібно на движок", щоб довірчий інтервал
mention rate конкурента звузився до цільової точності ±5 в.п. Це той
самий метод crossing points, що й у статті Sielinski (arXiv:2603.08924),
перенесений на нову задачу (brand mentions) і нові движки — **не** строга
параметрична формула n(параметри розподілу), яку сам автор статті явно
залишив майбутньою роботою (див. "Future Work" у мастер-плані, п.5).

## День 1 — Криві збіжності (subsampling curves)

### 1. Ідея методу

У нас немає бюджету нескінченно нарощувати n новими API-викликами, щоб
побачити, як звужується CI. Натомість використовуємо вже зібрані N
відповідей на групу (`subject_brand`, `engine`, `mentioned_entity`) як
кінцевий пул і **субсемплюємо** з нього менші підвибірки розміру
n = 1..N: для кожного n беремо багато випадкових підвибірок без
повернення розміру n із пулу, для кожної підвибірки рахуємо
`bootstrap_ci()` (Тиждень 3) і беремо середню ширину CI по всіх
підвибірках цього n. Результат — крива "n → середня ширина CI", що
показує, наскільки точність зростала б, якби ми зупинилися на меншому n.
Це чесний емпіричний спосіб оцінити збіжність на наявних даних, без
додаткового збору.

**Застереження, яке явно йде в звіт:** пул для Claude об'єднує відповіді
з трьох різних прогонів (включно з `run#1`/`run#2`/`run#3` того самого
дня чи з різницею в дні) — тобто крива відображає не лише зменшення
семплінгової похибки, а й трохи реальної варіації між прогонами. Це
робить оцінку консервативнішою (ширшою), а не оптимістичнішою, тож для
мети "орієнтир мінімального n" це прийнятний, чесно позначений компроміс.

### 2. Реалізація (`aivisibility/analysis/convergence.py`)

    subsample_curve(mentioned: list[bool], sizes: list[int] | None = None,
                     n_subsamples: int = 200, n_resamples: int = 500,
                     seed: int | None = None) -> list[ConvergencePoint]

`ConvergencePoint` (dataclass): `n, avg_half_width_pp, point_estimate`.
За замовчуванням `sizes = range(1, len(mentioned) + 1)`. Для кожного n:
`n_subsamples` випадкових вибірок без повернення розміру n з `mentioned`
(через `numpy.random.Generator.choice(..., replace=False)`), для кожної —
`bootstrap_ci()` з Тижня 3, ширина = `(upper - lower) / 2 * 100` (в.п.),
усереднюємо по підвибірках. Для n = N (весь наявний пул) робимо лише
одну "підвибірку" (сам пул) замість 200 однакових.

### 3. Агрегація по движку (не по кожній трійці окремо)

Мастер-план хоче криву "окремо для Claude і OpenAI" — тобто один
узагальнений орієнтир на движок, не 18 окремих кривих на кожну
(`brand`, `entity`) пару з Тижня 3. Тому:

- Пул для кожної (`subject_brand`, `engine`, `mentioned_entity`)-групи,
  де `entity` — конкурент (не сам subject_brand, з тієї ж причини, що й
  у Тижні 3 — trivial >90%), будуємо через `db.get_responses_with_brand()`
  без фільтра по `run_id` (усі прогони).
- Криву кожної групи рахуємо окремо (`subsample_curve`), потім усереднюємо
  `avg_half_width_pp` по всіх групах цього движку на кожному спільному n
  (n обмежений мінімальним N серед груп цього движку, тобто N=24 для
  Claude і Stripe/Paddle разом уже нижче за 36, бо Paddle-групи і
  Stripe-групи мають різне число конкурентів/спостережень — деталь
  уточнюється в коді).
- Результат: `dict[str, list[ConvergencePoint]]` — по одній усередненій
  кривій на `claude` і `openai`.

## День 2 — Емпіричний мінімальний n (crossing points) + README

### 1. Crossing point на спостережених даних

    estimate_min_n(curve: list[ConvergencePoint], target_pp: float = 5.0) -> CrossingResult

`CrossingResult`: `engine, target_pp, observed_n | None, extrapolated_n |
None, fit_note`. Спочатку шукаємо найменше n у кривій, де
`avg_half_width_pp <= target_pp` (спостережений crossing point). Якщо
такого n немає в межах наявного N (дуже ймовірно — навіть при грубій
попередній прикидці на типовий mention rate конкурента ~10-40% ±5 в.п. по
біноміальній оцінці потребує щонайменше сотні запитів, а в нас максимум
24-36) — це **не помилка**, а очікуваний і чесно задокументований
результат. Точне число уточнюється в розділі "Фінальний результат" уже
на реальних спостережених показниках mention rate.

### 2. Екстраполяція за формою кривої (не за формулою Sielinski)

Ширина довірчого інтервалу частки за біноміальним наближенням спадає як
`c / sqrt(n)`. Це загальновідома властивість (не параметрична модель
розподілу цитувань з майбутньої роботи Sielinski), тому дозволено:
підігнати `c` методом найменших квадратів на спостережених точках кривої
(`width ≈ c / sqrt(n)`), і розв'язати `n_target = (c / target_pp) ** 2`.
Результат позначається `extrapolated_n` з явним `fit_note`, наприклад:
`"екстраполяція за формою кривої 1/sqrt(n) з наявних n≤36, не пряме
спостереження"`.

**Чітка межа чесності, задокументована і в коді, і тут:** це підгонка
відомої форми кривої під наші ж спостережені точки — не Sielinskyʼва
строга формула `n(параметри розподілу цитувань)`, яку автор статті явно
залишив окремою майбутньою роботою (мастер-план, Future Work п.5). Ми не
претендуємо на це.

**Друга методологічна поправка під час реалізації:** первинний фіт
`c/sqrt(n)` без обмежень (regression через початок координат за всіма
точками n≥2) давав для OpenAI суперечливий результат — екстрапольований
n=22 менший за вже спостережений n=24, де ціль ще не досягнута. Причина:
регресія через початок координат природно надає непропорційно велику
вагу точкам з малим n (великий `1/sqrt(n)`), а це якраз найшумніші точки,
найближчі до виродженого n=1. Виправлено: фіт тепер використовує лише
верхню половину спостереженого діапазону n (n ≥ max_n // 2), плюс захисне
обмеження `extrapolated_n ≥ max_n + 1`, щоб результат ніколи не суперечив
факту "ціль ще не досягнута на max_n".

  Обидва движки: ціль ±5 в.п. не досягається навіть на максимально
  зібраних n (36 для Claude, 24 для OpenAI) — очікуваний результат.
  Уточнена (постфактум, на реально спостережених mention rate — 14.5%
  Claude, 7.4% OpenAI, а не грубій прикидці "~10-40%" з плану вище)
  біноміальна оцінка через `n = 1.96² · p(1-p) / 0.05²` дає орієнтир
  n≈191 для Claude і n≈105 для OpenAI — того самого порядку, що й наша
  bootstrap-екстраполяція (84 і 46), хоч і майже вдвічі вищий. Різниця
  чесно пояснювана: наш `1/sqrt(n)` фіт підігнаний лише на спостережених
  n≤36, тобто це екстраполяція екстраполяції — грубіший, оптимістичніший
  орієнтир, ніж класична біноміальна формула, яка не залежить від форми
  малої вибірки. Для практичного планування розумніше орієнтуватися на
  вищу з двох оцінок (біноміальну), а bootstrap-криву читати як "порядок
  величини, підтверджений із наявних даних". Екстрапольований орієнтир
  для OpenAI (≈46-105) помітно нижчий, ніж для Claude (≈84-191) в обох
  оцінках — цікаве спостереження саме по собі: варіанти OpenAI-відповідей
  у цій вибірці дають нижчий і стабільніший mention rate конкурентів
  (~7%), тому їхній CI звужується швидше за той самий n. Не варто
  узагальнювати це на "OpenAI дешевший вимірювати" без ширшої вибірки —
  але саме такі помітні різниці між движками і є причиною, чому Тиждень 4
  рахує орієнтири окремо для кожного.

## Відкриті питання / ризики

- N обмежений уже зібраними даними (36 Claude, 24 OpenAI на бренд) —
  крива збіжності і будь-яка екстраполяція з неї є оцінкою на малій
  вибірці, а не остаточним числом. Якщо на практиці знадобиться дійсно
  надійний орієнтир — треба буде реально зібрати десь n≈100-200 відповідей
  на движок (за класичною біноміальною оцінкою на спостережених mention
  rate — див. "Фінальний результат"), що вже помітна стаття витрат (радше
  майбутня робота/Тиждень 5, де адаптивний семплінг якраз і покликаний
  здешевити це нарощення).
- Пул Claude об'єднує три прогони, зроблені в різні моменти (включно з
  `run#1`, який Тиждень 1 позначив як "тестовий") — це додає трохи
  реальної між-прогонної варіації в оцінку ширини CI, що консервативно
  (розширює, не звужує) орієнтир n. Явно позначено, не приховано.
- Екстраполяція `1/sqrt(n)` — стандартна і чесна властивість
  довірчих інтервалів частки, але це **не** та строга параметрична
  формула n(розподіл цитувань), яку Sielinski залишив майбутньою
  роботою; наш результат — емпіричний орієнтир для нашого сетапу, як і
  каже мастер-план.
- Матплотліб — нова залежність, додається лише для одного графіка; якщо
  виявиться недоречною для решти проєкту (Laravel-дашборд у Тижні 8
  малює свої графіки на Chart.js/ApexCharts), її роль звужується до
  одноразового артефакту цього тижня.
