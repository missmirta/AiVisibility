# AI Visibility & Trust Engine — платіжні провайдери (fintech)

Пет-проект на Claude Agent SDK. Мета: не черговий трекер згадувань бренду в AI,
а статистично чесний вимірювальний рушій — з довірчими інтервалами, адаптивним
семплінгом і картою сприйняття, дешевший за токенами, ніж наївний підхід.

## Технічний стек

Ядро (агенти, статистика, ML) — Python, бо там уся потрібна екосистема і
офіційний Claude Agent SDK. Презентаційний шар — PHP/Laravel, щоб показати
свою сильну сторону, а не ховати її заради "проекту на одній мові".

| Компонент | Технологія |
|---|---|
| Discovery Agent, Query Generator, Prober | Python + Claude Agent SDK |
| Другий движок для порівняння | Python + OpenAI SDK |
| Bootstrap CI, криві збіжності | Python (scipy, numpy, pandas) |
| Adaptive sampling | Python, власна реалізація (active learning з нуля) |
| Bradley-Terry (карта сприйняття) | Python, власна реалізація (~50-100 рядків, а не готова бібліотека — свідомо, щоб показати розуміння методу) |
| Classifier two-sample test, embeddings-кластеризація | Python (scikit-learn) |
| Сховище | SQLite на старті → Postgres, якщо піде далі демо |
| API між Python-сервісом і Laravel | FastAPI |
| Дашборд | PHP/Laravel (Blade або Alpine.js/Vue для інтерактиву) |
| Графіки | Chart.js / ApexCharts (client-side) |
| Фонові задачі (довгі прогони аналізу) | Laravel Queue + Horizon, або окремий Python-процес |
| Деплой демо | Docker Compose (Python-сервіс + Laravel + БД разом) |

**Запасний варіант для тижня 8**, якщо часу бракує: замінити Laravel-дашборд
на CLI + Python-скрипт, що генерує статичний HTML-звіт (matplotlib/plotly).
Дослідницьке ядро (тижні 3-5) від цього не залежить і лишається незмінним.

## Позиціонування (для README і співбесіди)

> Стаття Sielinski, "Quantifying Uncertainty in AI Visibility" (arXiv:2603.08924,
> 2026) довела, що AI-visibility метрики — статистичні оцінки з невизначеністю,
> а не фіксовані числа. Я переношу її методологію (bootstrap CI, криві
> збіжності) на нову задачу (brand mentions, не domain citations), нові движки
> (Claude, OpenAI — у статті їх не було) і нову нішу (B2B fintech замість
> consumer) — і додаю два модулі, яких немає ні в статті, ні в жодному
> комерційному/open-source інструменті: адаптивний семплінг, що знижує
> вартість вимірювання, і карту сприйняття бренду через попарні порівняння
> (Bradley-Terry).

**Важливе уточнення (не перебільшувати на співбесіді):** стаття сама розділяє
дві речі — (1) емпіричні орієнтири розміру вибірки для конкретних платформ,
які вони отримали і показали, і (2) строге параметричне правило (формула
n як функція параметрів розподілу цитувань, без нового збору даних під кожен
новий випадок), яке вони явно відклали як окрему майбутню роботу. Мій проект
закриває (1) для нових движків/задачі — це не тривіально й ніде не
опубліковано, але це не те саме, що (2). Формулу я не виводжу. Чесне
формулювання: "я даю перші опубліковані емпіричні орієнтири розміру вибірки
для Claude й OpenAI на задачі brand mentions у fintech", а не "я вивела
правило мінімального розміру вибірки".

Ідея вимірювання невизначеності — не наша, вона з рецензованої статті. Наш
внесок — перенесення на нову задачу, нову нішу, нові движки, і два додаткові
модулі (адаптивний семплінг + карта сприйняття), яких у статті й у жодному з
відомих комерційних/open-source інструментів немає.

## План на 8 тижнів (2 дні/тиждень)

### Тиждень 1 — Discovery + Query Generator
- Discovery Agent (Claude + web search): вхід — тільки назва бренду (+ URL),
  вихід — ніша, конкуренти, цільова аудиторія. Human-in-the-loop: користувач
  підтверджує/редагує перед дорогим прогоном.
- Query Generator: структурований JSON, категорії intent — awareness /
  comparison / transactional / use-case. Для fintech додатково: query-type
  "комісії/ціна" і "географія/підтримувані країни".
- Результат: `queries.json` для 5 брендів.

### Тиждень 2 — Prober + сховище
- Цикл прогону запитів через Claude + OpenAI, retry з backoff, логування
  токенів і вартості з першого дня.
- Схема БД: запит → прогін → відповідь → виявлені згадки.
- Одразу заводимо легкий cron-збір (навіть раз на день) — знадобиться для
  "довших вікон" у майбутньому, навіть якщо повноцінно це не встигнемо.
- Результат: перший сирий датасет.

### Тиждень 3 — Статистичне ядро ⭐ (диференціатор №1)
- Детекція згадок бренду й конкурентів у сирих відповідях.
- Bootstrap-довірчі інтервали (resampling на рівні відповіді) для mention
  rate / citation share.
- Вердикт "зміна чи шум": порівняння інтервалів між періодами.
- Результат: перший чесний звіт виду "22% ± 6 п.п., інтервали перетинаються
  з попереднім періодом — це шум, не тренд".

### Тиждень 4 — Криві збіжності й емпіричні орієнтири вибірки
- Ширина довірчого інтервалу як функція n, окремо для Claude і OpenAI.
- Емпіричний мінімальний n для цільової точності (±5 п.п.) — по кожному
  движку, тим самим методом crossing points, що й у статті, але на нових
  движках і новій задачі (brand mentions замість domain citations).
- **Не** виводимо строгу формулу n(параметри розподілу) — автор статті сам
  залишив це як окрему майбутню роботу. Наш внесок — перші опубліковані
  емпіричні орієнтири для Claude й OpenAI, а не загальне правило.
- Результат: таблиця "скільки запитів потрібно на движок" + чесна примітка
  в README, що це емпіричний орієнтир для нашого сетапу, а не універсальна
  формула.

### Тиждень 5 — Адаптивний семплінг ⭐ (диференціатор №2)
- Стратегія розподілу наступного API-виклику туди, де невизначеність
  найбільше впливає на фінальну метрику (Thompson sampling / expected
  variance reduction).
- Захист від ранньої зупинки: зупиняємось не за поточною шириною CI (стаття
  показала немонотонну збіжність, особливо для платформ з нестаціонарним
  розподілом), а за стабільністю на ковзному вікні.
- Результат: головна цифра презентації — "та сама точність за X% менше
  API-викликів, ніж рівномірний семплінг".

### Тиждень 6 — Репрезентативність запитів (диференціатор №3)
- Збір реальних питань про платіжні провайдери з публічних джерел (Reddit
  r/SaaS, r/webdev, Stack Overflow, Indie Hackers, Hacker News).
- Embeddings + classifier two-sample test: наскільки LLM-згенеровані запити
  відрізняються від реальних.
- Перезважування метрики за кластерами реальних запитів.
- Результат: "наш синтетичний набір зміщений ось так, ось виправлена
  метрика з урахуванням реальної розподілу тем".

### Тиждень 7 — Карта сприйняття (диференціатор №4)
- Атрибути для fintech: дешевизна, швидкість виплат, надійність/безпека,
  простота інтеграції, якість підтримки, регуляторна довіра, "для стартапу"
  vs "для enterprise".
- Попарні порівняння ("Stripe чи Adyen надійніший для e-commerce?"),
  відповідь в 1 токен — дешево.
- Агрегація через модель Bradley-Terry, корекція позиційного упередження
  (прогін в обох порядках A/B і B/A).
- Опційно (якщо є час): базовий fact-check — витягнути комісії з офіційних
  pricing-сторінок (ground truth) і звірити з тим, що каже AI в тексті
  відповідей — тут це дешево, бо дані структуровані.
- Результат: карта "яким AI бачить кожен бренд" з довірчими інтервалами.

### Тиждень 8 — Упаковка
- Дашборд (Laravel — швидко, свій стек) або CLI + статичний HTML-звіт,
  якщо відстаємо за часом.
- README: чесне порівняння з ринком, посилання на Sielinski (arXiv:2603.08924),
  опис методології, обмежень, future work.
- Демо-прогін на 5 брендах, скріншоти/графіки для презентації.
- Короткий технічний блог-пост (опційно, сильно підсилює резюме).

## Що НЕ входить у основний скоуп (свідомо)

- **Zero-inflated статистика для рідко цитованих доменів** — найскладніша
  відкрита задача зі статті, вимагає окремого дослідження (occupancy models
  з екології). Занадто дорого за часом для 8 тижнів.
- **Повний fact-verification з великою базою ground truth** — вже роблять
  LLMClicks, Profound. Робимо тільки легку версію в тижні 7, якщо лишається
  час.
- **Довгі вікна спостереження (місяці)** — інфраструктура (cron) закладається
  з тижня 2, але повноцінних результатів за 8 тижнів не буде. Чесно називаємо
  обмеженням.

## Future Work (у README)

1. **Географія / мова запиту.** Видимість платіжного провайдера сильно
   залежить від країни (США vs ЄС vs Україна) — жодне з відомих досліджень
   (включно з Sielinski) і жоден комерційний інструмент цього системно не
   вимірює. Для fintech це особливо болюче: компанії виходять на нові ринки
   і хочуть знати, як AI рекомендує платіжні рішення локально. Наступний
   крок — розширити Prober на мультимовні/геолокалізовані запити і порівняти
   довірчі інтервали між регіонами.
2. Zero-inflated моделювання рідко цитованих доменів.
3. Довгострокові часові ряди (сезонність, ефекти оновлень моделей).
4. Розширення на інші fintech-піднiші (перекази, необанки) для перевірки
   узагальнюваності методу.
5. **Строге параметричне правило мінімального розміру вибірки.** Тиждень 4
   дає лише емпіричні орієнтири n (crossing points) для конкретних движків
   і нашого сетапу — той самий метод, що застосував Sielinski для своїх трьох
   платформ. Формула, яка виводила б потрібний n як функцію параметрів
   розподілу цитувань/згадок (без повторного збору даних під кожен новий
   бренд чи движок), — це те, що сам автор статті явно відклав як окрему
   майбутню роботу. Наш проект цю формулу не виводить і не закриває.

## Метрики для фінальної презентації

1. Економія API-викликів адаптивного семплінгу проти рівномірного (%)
2. Криві "n запитів → ширина CI" для Claude і OpenAI окремо
3. Скільки з виявлених "змін видимості" виявились шумом після bootstrap CI
4. Вартість повного аналізу одного бренду в доларах (токени)
5. Розбіжність синтетичних і реальних запитів (classifier two-sample test)

## Ризики і що різати першим при відставанні

Порядок різання: Gemini → карта сприйняття (тиждень 7) → репрезентативність
(тиждень 6) → дашборд замінити на CLI/статичний звіт.

**Ніколи не різати тижні 3-5** — без них проект перетворюється на ще один
трекер згадувань, яких на ринку вже десятки.

Головні технічні ризики:
- Rate limits на двох движках → Batch API + нічні прогони з тижня 2
- Спокуса зробити гарний UI замість методології — конкуренти мають кращий
  UI, наша перевага — статистична чесність
- Розповзання скоупу — щовихідні перевіряти "чи наближає це до тижня 5"
